# 학습 자료 — 웹사이트 하나를 AWS에 올리며 배우는 클라우드 기초

> 이 문서의 목표: 평가에서 **"왜 그렇게 했는지"를 내 말로 설명**할 수 있게 하는 것.

## 1. 큰 그림: 클라우드는 "빌린 컴퓨터"가 아니라 "빌린 데이터센터"

내 PC에서 `node server.js`를 켜면 나만 접속할 수 있다. 다른 사람이 들어오려면 아래가 **전부** 필요하다.

| 현실의 데이터센터 | AWS에서 부르는 이름 | 이 프로젝트에서 |
|---|---|---|
| 우리 회사 건물 (사설망) | **VPC** | `10.0.0.0/16` |
| 층/구역 | **Subnet** | `10.0.1.0/24` (Public) |
| 건물 정문 (인터넷 회선) | **Internet Gateway (IGW)** | VPC에 1개 연결 |
| 안내판 "외부로 가려면 정문으로" | **Route Table** | `0.0.0.0/0 → igw` |
| 각 서버 방 앞 경비원 | **Security Group (SG)** | 80 전체 허용, 22 내 IP만 |
| 서버 컴퓨터 | **EC2** (+ 디스크 **EBS**) | t3.micro + 8GiB |
| 건물 주소 | **퍼블릭 IP / Elastic IP** | 접속 주소 |
| 출입증 발급 규정 (누가 무엇을 만들 수 있나) | **IAM** | `docs/iam-policy.json` |

핵심 문장: **"네트워크(어디로 갈 수 있나) + 방화벽(들어올 수 있나) + 권한(누가 바꿀 수 있나)이 모두 맞아야 서비스가 열린다."**

## 2. 패킷 하나의 여행 — 브라우저에서 `http://3.35.x.x/health`를 치면

```
[사용자 브라우저]
   │ ① DNS 없이 IP로 바로 → TCP 80번으로 연결 시도
   ▼
[인터넷] ──► [Internet Gateway]
   │ ② IGW가 퍼블릭 IP(3.35.x.x)를 EC2의 프라이빗 IP(10.0.1.23)로 바꿔(1:1 NAT) VPC 안으로
   ▼
[Route Table] ── 목적지 10.0.1.23은 10.0.0.0/16 → local, VPC 안이니 그대로 전달
   ▼
[Security Group] ── ③ 인바운드 80/tcp, 출발지 0.0.0.0/0 허용? → 통과
   ▼                   (상태 저장: 들어온 연결의 응답은 자동 허용)
[EC2: Nginx :80] ── ④ location = /health → return 200 "OK"
   │
   ▼ 응답은 거꾸로: EC2 → RT의 0.0.0.0/0 → IGW → 인터넷 → 브라우저
```

`/api/analyze`라면 ④에서 Nginx가 **같은 컴퓨터 안의** `127.0.0.1:3000`(Node)에 다시 요청한다. 이 두 번째 연결은 **VPC 밖으로 나가지 않으므로 SG와 무관**하다. 그래서 3000번 포트는 SG에서 열 필요가 없고, 열면 안 된다.

Node가 사진 분석 AI(Gemini API)를 부를 때는 반대 방향(아웃바운드): EC2 → SG 아웃바운드(기본 전체 허용) → RT `0.0.0.0/0 → igw` → 인터넷 → `generativelanguage.googleapis.com:443` (Claude로 바꾸면 `api.anthropic.com:443`).

### 어디가 빠지면 어떤 증상이 나오나 (트러블슈팅의 뼈대)

| 빠진 것 | 바깥에서 보이는 증상 | 이유 |
|---|---|---|
| IGW 미연결 / RT에 `0.0.0.0/0` 없음 | **시간 초과** (응답 없음) | 패킷이 VPC로 들어오거나 나갈 길이 없음 |
| 퍼블릭 IP 없음 | 접속할 주소 자체가 없음 | 프라이빗 IP는 인터넷에서 못 찾음 |
| SG에 80 없음 | **시간 초과** | SG는 거절 응답 없이 **조용히 버림** |
| Nginx 꺼짐 | **Connection refused** (즉시 실패) | 컴퓨터엔 도착했지만 80을 듣는 프로그램이 없음 |
| Node 꺼짐 | `/health` OK, `/api/*` **502** | Nginx는 살아 있고 그 뒤가 죽음 |
| 업로드가 1MB 초과 (기본값) | **413** | `client_max_body_size` |
| 분석이 60초 초과 (기본값) | **504** | `proxy_read_timeout` |

> **"시간 초과면 네트워크/SG, 즉시 거절이면 서버 프로세스, 5xx면 프록시 뒤쪽"** — 이 한 줄로 가설의 절반이 정해진다.

## 3. 구성 요소별 핵심

### VPC (Virtual Private Cloud)
- AWS 안에 만든 **나만의 격리된 사설 네트워크**. 다른 고객의 서버와 논리적으로 분리된다.
- CIDR `10.0.0.0/16` = 앞 16비트 고정 → 주소 65,536개. 사설 대역(10/8, 172.16/12, 192.168/16)에서 고른다.
- VPC를 만들기만 해서는 **인터넷과 연결되지 않는다**. 기본이 "닫힘"이라는 것이 보안의 출발점이다.

### Subnet
- VPC를 쪼갠 구역. **하나의 가용 영역(AZ)에 속한다** (예: ap-northeast-2a).
- `10.0.1.0/24` = 256개 중 AWS가 5개 예약 → 251개 사용 가능.
- **"Public" 서브넷이라는 설정 스위치는 없다.** 연결된 라우팅 테이블에 `0.0.0.0/0 → IGW`가 있으면 Public, 없으면 Private. (시험 단골)

### Internet Gateway
- VPC와 인터넷 사이의 **문**. VPC당 1개만 붙는다. 무료, 관리형, 이중화되어 있다.
- 퍼블릭 IP ↔ 프라이빗 IP **1:1 변환**을 해 준다. EC2 OS 안에서 `ip addr`을 쳐 보면 퍼블릭 IP는 안 보이고 프라이빗 IP만 보이는 이유.
- (비교) **NAT Gateway**: Private 서브넷이 **나가기만** 할 수 있게 해 주는 장치. 시간당 요금이 비싸서 이번 실습에서는 만들지 않는다.

### Route Table
- "목적지가 이 범위면 여기로 보내라"는 표. **가장 구체적인 경로(longest prefix)**가 이긴다.
  - `10.0.0.0/16 → local` (자동, 지울 수 없음): VPC 내부끼리
  - `0.0.0.0/0 → igw-xxx`: 나머지 전부 = 인터넷
- 서브넷에 **명시적으로 연결**하지 않으면 메인 라우팅 테이블을 따른다. 커스텀 RT를 만들고 연결을 빼먹는 실수가 흔하다.

### Security Group
- **인스턴스(정확히는 네트워크 인터페이스) 단위 방화벽**.
- **허용 규칙만** 있다(거부 규칙 없음). 목록에 없으면 거부.
- **상태 저장(stateful)**: 들어온 요청에 대한 응답은 아웃바운드 규칙과 상관없이 나간다.
- 거부할 때 **응답하지 않고 버린다** → 클라이언트는 시간 초과를 본다.
- (비교) **NACL**: 서브넷 단위, 허용+거부, 상태 비저장(응답 포트도 따로 열어야 함). 기본값이 전체 허용이라 이번엔 건드리지 않는다.

이 프로젝트의 SG:

| 방향 | 포트 | 소스/대상 | 이유 |
|---|---|---|---|
| IN | 80/tcp | 0.0.0.0/0 | 누구나 웹사이트를 써야 함 |
| IN | 22/tcp | **내 IP/32** | 관리 통로. 전 세계에 열면 수 분 안에 무차별 대입 공격이 시작됨 |
| OUT | 전체 | 0.0.0.0/0 | 패키지 설치, Gemini API 호출 (기본값) |
| ~~IN~~ | ~~3000~~ | — | **열지 않음**. Nginx가 내부에서 프록시하므로 필요 없음 |

### EC2 / EBS / 키 페어 / Elastic IP
- **EC2**: 가상 서버. t3.micro = vCPU 2, 메모리 1GiB.
- **EBS**: 네트워크로 연결된 디스크. **인스턴스를 "중지"해도 EBS 요금은 계속 나간다.** 종료(Terminate) 시 루트 볼륨은 기본으로 같이 삭제되지만, 추가 볼륨은 남을 수 있다.
- **키 페어**: SSH 로그인용 공개키/개인키. AWS는 공개키만 보관 → `.pem`(개인키)을 잃으면 **재발급 불가**.
- **퍼블릭 IP vs Elastic IP**: 자동 할당 퍼블릭 IP는 **중지/시작하면 바뀐다**. Elastic IP는 고정이지만 **2024-02부터 모든 퍼블릭 IPv4에 시간당 요금**이 붙고, 할당만 해 두고 안 써도 과금된다 → 정리할 때 반드시 **Release**.

### IAM (Identity and Access Management)
- **"누가(Principal) 어떤 작업(Action)을 어떤 대상(Resource)에, 어떤 조건(Condition)에서 할 수 있나"**를 정한다.
- 평가 규칙: **명시적 Deny > 명시적 Allow > 기본 Deny**. 아무것도 안 붙은 사용자는 아무것도 못 한다.
- **루트 계정**: 모든 권한 + 제한 불가 → 일상 작업에 쓰지 않는다. MFA 걸고 금고에 넣어 두는 열쇠.
- **사용자 vs Role**: 사용자는 사람(장기 자격 증명), Role은 잠깐 빌려 쓰는 신분(EC2, Lambda, 다른 계정이 맡음, 임시 자격 증명).

## 4. Security Group vs IAM — 가장 많이 헷갈리는 둘

| | Security Group | IAM |
|---|---|---|
| 지키는 대상 | **네트워크 트래픽** (패킷) | **AWS API 호출** (콘솔 클릭, CLI 명령) |
| 질문 | "이 IP에서 이 포트로 **들어와도** 되나?" | "이 사용자가 SG를 **만들거나 지워도** 되나?" |
| 단위 | 인스턴스(ENI) | 사용자 / 그룹 / Role |
| 실패하면 | 시간 초과 | `You are not authorized to perform: ec2:...` |
| 이 프로젝트 | 80 전체, 22 내 IP | `iam-policy.json` |
| 비유 | 건물 출입문 경비원 | 건물 관리 사무소의 "누가 문을 달고 뗄 수 있나" 규정 |

> 둘 다 **최소 권한**을 적용하지만 대상이 다르다. **SG는 "누가 서비스에 닿을 수 있나", IAM은 "누가 인프라를 바꿀 수 있나".**
> 서버가 해킹당해 SSH가 뚫려도, 그 서버에 IAM 권한(Role)이 없으면 공격자가 AWS 계정 전체를 망가뜨리진 못한다. 두 겹의 방어.

### 최소 권한 원칙 — 왜, 어떻게

- **왜**: 키가 유출되거나 실수했을 때 **피해 반경을 줄이려고**. AdministratorAccess 키가 GitHub에 올라가면 몇 분 안에 다른 리전에 비싼 GPU 인스턴스로 채굴기가 뜬다(실제로 흔한 사고). 이 프로젝트 정책이라면 같은 사고에서도 **서울 리전의 micro 인스턴스**만 만들 수 있다.
- **어떻게** (`docs/iam-policy.json`이 하는 일):
  1. **필요한 서비스만**: `ec2:` 액션만 있다. S3, RDS, IAM, Lambda는 하나도 없다. (VPC·SG·키페어·EIP도 API상 EC2 서비스에 속한다.)
  2. **필요한 동작만**: 조회(`Describe*`) + 실습에 쓰는 생성/연결/삭제만 나열. `CreateNatGateway`, `CreateVpcPeeringConnection` 등은 없음.
  3. **리전 제한**: 모든 Allow에 `aws:RequestedRegion = ap-northeast-2` 조건 + 서울 밖 `ec2:*` 명시적 Deny.
  4. **비용 가드레일**: t2.micro/t3.micro가 아닌 인스턴스 Deny, 30GiB 넘는 볼륨 Deny.
  5. **반복 개선**: 쓰다가 `not authorized` 오류가 나면 **그 액션 하나만** 추가한다. 처음부터 `*`를 주고 줄이는 것이 아니라 0에서 늘려 간다.
- **한계 (정직하게 말할 것)**: `Describe*`는 조회 전체를 허용한다(읽기라 위험이 낮아 관례적으로 허용). 콘솔이 부가 정보를 보여 주려고 다른 서비스를 조회하다 경고를 띄울 수 있지만 실습엔 지장이 없다. Billing 화면은 이 사용자로 볼 수 없다.

## 5. 이 프로젝트의 설계 이유 (Vercel → EC2)

| 결정 | 이유 | 평가에서 말할 포인트 |
|---|---|---|
| Nginx를 앞에 둠 (리버스 프록시) | 정적 파일은 Nginx가 훨씬 빠르고, Node는 API만 신경 씀. 업로드 크기·타임아웃·로그를 한곳에서 관리 | "외부에 노출되는 건 80번 Nginx 하나" |
| `/health`를 Nginx가 직접 응답 | **IGW→RT→SG→EC2→Nginx 경로만** 순수하게 검증. Node가 죽어도 "인프라는 정상"이 구분됨 | 헬스체크는 무엇을 검사하는지가 명확해야 함 |
| Node는 `127.0.0.1:3000` | 같은 컴퓨터의 Nginx만 접근 가능. SG 실수로 3000을 열어도 바깥에서 닿지 않음 | **SG + 바인딩 주소 = 두 겹 방어** |
| Docker도 `-p 127.0.0.1:3000:3000` | `-p 3000:3000`은 `0.0.0.0`에 바인딩돼 SG가 열려 있으면 그대로 노출됨 | 컨테이너 포트 매핑의 함정 |
| `client_max_body_size 10m` | 기본 1MB → 사진 업로드가 413으로 막힘 | 증상(413)으로 원인을 바로 짚을 수 있음 |
| `proxy_read_timeout 300s` | 기본 60s → 1~2분 걸리는 분석이 504로 끊김. Node 쪽은 280s로 더 짧게 해서 Nginx보다 먼저 정리된 오류를 돌려줌 | 타임아웃은 **바깥쪽이 더 길게** |
| API 키는 `.env` + `.gitignore` | 코드와 비밀을 분리. Git에 한 번 올라간 키는 지워도 히스토리에 남음 | 비밀번호도 최소 노출 |
| systemd 서비스 | 서버 재부팅·프로세스 크래시 후 자동 재시작, 전용 사용자(`netsolver`)로 권한 축소, `journalctl`로 로그 | 서버 안에서도 최소 권한 |
| 외부 의존성 0 | `npm install` 없이 배포, 공급망 공격 표면 0, micro 인스턴스 디스크·메모리 절약 | |

## 6. 콘솔 작업 순서 (서울 리전, IAM 사용자로 로그인)

0. **(루트로 1회만)** IAM → 정책 생성(JSON에 `iam-policy.json` 붙여넣기, 이름 `net-solver-lab-policy`) → 사용자 `net-solver-lab` 생성, 콘솔 접근 허용, 정책 연결 → **로그아웃**하고 IAM 사용자로 로그인. 루트에는 MFA.
1. 우측 상단 리전 **아시아 태평양(서울)** 확인.
2. **VPC** 생성 ("VPC만" 선택): `net-solver-vpc`, `10.0.0.0/16`, 태그 `Project=net-solver`.
3. **서브넷** 생성: `net-solver-public-a`, AZ `ap-northeast-2a`, `10.0.1.0/24` → 작업 → 서브넷 설정 편집 → **퍼블릭 IPv4 자동 할당 활성화**.
4. **인터넷 게이트웨이** 생성 → 작업 → **VPC에 연결**.
5. **라우팅 테이블** 생성 (`net-solver-public-rt`) → 라우팅 편집: `0.0.0.0/0 → igw-...` 추가 → 서브넷 연결 편집: public-a 선택.
6. **보안 그룹** 생성 (VPC = net-solver-vpc): 인바운드 HTTP 80 `0.0.0.0/0`, SSH 22 **내 IP**. 아웃바운드 기본값.
7. **키 페어** 생성: `net-solver-key`, RSA, `.pem` 다운로드 → 안전한 곳에 보관.
8. **EC2** 시작: Ubuntu 24.04 LTS, **t3.micro**, 키 페어 선택, 네트워크 설정 편집 → VPC/서브넷/기존 SG 선택, 퍼블릭 IP 자동 할당 활성화, 스토리지 8GiB gp3.
9. 접속: `ssh -i net-solver-key.pem ubuntu@<퍼블릭IP>` → `curl -I https://example.com`(아웃바운드 확인).
10. README "EC2 배포" 절차 → `bash deploy/setup-ec2.sh`.
11. 내 PC에서 `curl -i http://<퍼블릭IP>/health` → 스크린샷.
12. (선택) Elastic IP 할당 → 인스턴스에 연결 → README의 IP 갱신.
13. 끝나면 `cleanup-checklist.md` 순서대로 정리.

> 모든 리소스에 `Project=net-solver` 태그를 달아 두면 정리할 때 빠뜨리지 않는다.

## 7. 말로 설명하기 — 과제 목표 5문항 모범 답안

### Q1. VPC, Subnet, Route Table, IGW의 역할과 트래픽 흐름은?
> "VPC는 AWS 안의 격리된 사설 네트워크이고, 서브넷은 그걸 AZ 단위로 나눈 구역입니다. IGW는 VPC와 인터넷 사이의 문이고, 퍼블릭 IP와 프라이빗 IP를 1:1로 변환해 줍니다. 라우팅 테이블은 '이 목적지는 어디로'를 정하는 표인데, 서브넷의 라우팅 테이블에 `0.0.0.0/0 → IGW`가 있어야 그 서브넷이 Public이 됩니다. 요청은 인터넷 → IGW → 서브넷(라우팅) → 보안 그룹 → EC2 순서로 들어오고, 응답은 라우팅 테이블의 기본 경로를 따라 IGW로 나갑니다."

### Q2. Security Group과 IAM의 차이, 최소 권한을 왜/어떻게?
> "SG는 네트워크 패킷을 거르는 인스턴스 단위 방화벽이고, IAM은 AWS API 호출, 즉 누가 리소스를 만들고 바꿀 수 있는지를 정합니다. 최소 권한은 사고가 났을 때 피해 범위를 줄이려고 적용합니다. SG는 80만 전체에 열고 22는 제 IP/32로만, 3000은 아예 열지 않았습니다. IAM은 EC2 관련 액션만, 서울 리전에서만, micro 인스턴스만 허용하도록 정책을 직접 작성했고 AdministratorAccess는 주지 않았습니다."

### Q3. 외부 요청이 EC2 웹 서버에 닿으려면 무엇이 필요한가?
> "다섯 가지가 모두 맞아야 합니다. ① IGW가 VPC에 연결되어 있고, ② 서브넷 라우팅 테이블에 `0.0.0.0/0 → IGW` 경로가 있고, ③ 인스턴스에 퍼블릭 IP가 있고, ④ 보안 그룹이 80번을 허용하고, ⑤ 인스턴스 안에서 Nginx가 80번을 듣고 있어야 합니다. 하나라도 빠지면 접속이 안 되고, 어느 것이 빠졌는지에 따라 시간 초과냐 연결 거부냐로 증상이 달라집니다."

### Q4. 트러블슈팅 과정은?
> "증상을 정확히 적고(오류 문구, HTTP 코드), 요청 경로를 바깥에서 안쪽으로 따라가며 어디서 끊겼는지 가설을 세웁니다. 예를 들어 시간 초과면 네트워크나 SG, 502면 Nginx 뒤의 Node를 의심합니다. 그다음 `curl -v`, `ss -tlnp`, Nginx error.log, `journalctl` 같은 근거로 가설을 하나씩 검증하고, 원인 하나만 고친 뒤 같은 요청으로 결과를 확인합니다. 마지막으로 같은 실수가 반복되지 않도록 체크리스트나 설정 파일에 반영합니다."

### Q5. 과금 요인과 정리 순서·이유는?
> "대표적인 과금 요인은 실행 중인 EC2, 인스턴스가 중지돼도 남는 EBS 볼륨과 스냅샷, 퍼블릭 IPv4와 쓰지 않는 Elastic IP, 그리고 만들었다면 NAT Gateway·ALB·RDS입니다. 정리는 의존 관계의 역순입니다. 인스턴스를 먼저 종료해야 볼륨과 IP가 풀리고, 그다음 남은 볼륨 삭제, EIP 해제(Release), SG 삭제, IGW 분리 후 삭제, 서브넷·라우팅 테이블, 마지막에 VPC를 지웁니다. 순서를 어기면 DependencyViolation 오류가 납니다. 끝나면 Billing 화면을 다음 날 한 번 더 확인합니다."

## 8. 예상 질문 (꼬리 질문 대비)

| 질문 | 짧은 답 |
|---|---|
| Public 서브넷과 Private 서브넷의 차이는? | 라우팅 테이블에 IGW로 가는 기본 경로가 있느냐 없느냐. 설정 스위치가 아님 |
| SG에서 80만 열었는데 응답은 어떻게 나가나? | SG는 상태 저장이라 들어온 연결의 응답은 자동 허용 |
| SG와 NACL 차이? | SG: 인스턴스 단위, 허용만, 상태 저장 / NACL: 서브넷 단위, 허용+거부, 상태 비저장 |
| 왜 3000번을 SG에 안 열었나? | Nginx가 같은 인스턴스 안에서 127.0.0.1로 프록시하므로 외부 노출 불필요. 노출하면 Nginx의 크기 제한·로그를 우회 |
| SSH를 0.0.0.0/0으로 열면 왜 위험? | 인터넷 전체 봇이 22번을 상시 스캔·무차별 대입. 비밀번호 로그인은 꺼져 있어도 공격 표면이 됨 |
| 내 IP가 바뀌면? | SSH 시간 초과 → `checkip.amazonaws.com`으로 확인 후 SG 규칙 수정 (트러블슈팅 사례 후보) |
| 인스턴스를 중지했다 켰더니 접속 주소가 바뀌었다 | 자동 할당 퍼블릭 IP는 매번 바뀜. 고정하려면 Elastic IP |
| `/health`를 Node가 아니라 Nginx가 답하는 이유? | 인프라 경로만 검증하려고. Node 장애와 네트워크 장애를 구분할 수 있음 |
| 502와 504의 차이? | 502: 뒤쪽 서버에 연결 못 함/이상한 응답. 504: 연결했지만 제한 시간 안에 응답 없음 |
| 루트 계정을 쓰면 안 되는 이유? | 모든 권한이고 IAM 정책으로 제한 불가. 유출 시 계정 전체 탈취 |
| IAM 사용자와 Role 차이? | 사용자는 장기 자격 증명(사람), Role은 맡아서 쓰는 임시 자격 증명(서비스/다른 주체) |
| EC2가 Gemini(또는 Claude) API를 부르려면 IAM이 필요한가? | 아니다. Google·Anthropic은 AWS 밖의 서비스라 API 키(`.env`)로 인증. IAM은 AWS API에만 해당 |
| "중지"하면 과금이 멈추나? | 컴퓨팅 요금은 멈추지만 EBS와 퍼블릭 IP(EIP) 요금은 계속 |
| Docker에서 `-p 3000:3000`과 `-p 127.0.0.1:3000:3000` 차이? | 앞은 호스트의 모든 인터페이스(외부 포함)에 열림. 뒤는 호스트 내부에서만 접근 |
| HTTPS를 붙이려면? | 도메인 A 레코드 → EIP, SG에 443 추가, `certbot --nginx`. 인증서는 Let's Encrypt가 도메인 소유를 HTTP로 확인 |
| 트래픽이 늘면 어떻게 확장? | 지금은 단일 EC2라 단일 장애점. ALB + Auto Scaling 그룹 + 여러 AZ, 정적 파일은 S3+CloudFront (이번 범위 밖) |

## 9. 한 장 요약

```
열려 있는 것                         닫혀 있는 것
─────────────────────────────        ─────────────────────────────
80/tcp  ← 전 세계 (Nginx)             3000 (Node는 127.0.0.1에만)
22/tcp  ← 내 IP/32만                  그 외 모든 포트
ec2:* 일부 ← 서울 리전, micro만       S3·RDS·IAM·다른 리전·큰 인스턴스
.env (서버 안, 600 권한)              Git, Docker 이미지, 브라우저

길:  인터넷 → IGW → RT(0.0.0.0/0) → SG(80) → Nginx → (/api) → Node → (443) → Gemini API
정리: EC2 → EBS → EIP → (NAT/ALB/RDS) → SG → 키페어 → IGW → Subnet/RT → VPC → Billing 확인
```
